# dqwatch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A no-code data quality platform: users set up file/URL/API sources once, data is ingested automatically into DuckDB, and user-built checks run after every load without ever blocking it.

**Architecture:** Plain-Python core (`fetch → stage → load → checks → notify`) in `dqwatch/pipeline.py`, called by one generic Dagster job that a sensor launches per due source. A FastAPI + HTMX web app owns setup, rules, dashboard and AI chat and talks **only to SQLite**. DuckDB is written only by Dagster runs, which are serialized (max 1 concurrent run). That avoids DuckDB's single-writer file lock.

**Tech Stack:** Python 3.12, FastAPI, Jinja2, HTMX (CDN), DuckDB, SQLite (stdlib), Dagster + dagster-webserver, pytest, httpx (TestClient only). LLM and SMTP via stdlib (`urllib`, `smtplib`).

**Spec:** `docs/superpowers/specs/2026-11-23-dqwatch-design.md`

## Global Constraints

- Zero cost: no paid services; `docker compose up` runs web, Dagster, Ollama.
- Tests never call a real LLM or send real email. All tests run offline.
- A failing or crashing check, SMTP failure, or LLM outage must never fail, stall, or roll back a load.
- The AI never saves configuration: suggestions only become rules via a user click.
- Write modes: `replace` | `append` | `upsert` (UI label "Update by key"), default `upsert`.
- Rule JSON is the stored form, e.g. `{"id": "a1b2c3d4", "type": "range", "column": "amount", "min": 0, "max": 10000, "severity": "warn"}`.
- Severity: `warn` → dashboard only; `error` → dashboard + email. Email only on transition into failing (previous status `pass` or none).
- User-supplied column names are always quoted via `schema.qi()`; rule values are always bound parameters, never interpolated.
- Env config: `DQ_META` (SQLite path), `DQ_DATA` (DuckDB path), `DQ_INBOX` (watched-folder root), `DQ_LLM_BASE_URL` (default `http://ollama:11434/v1`), `DQ_LLM_API_KEY`, `DQ_LLM_MODEL` (default `llama3.2:3b`), `DQ_SMTP_HOST`, `DQ_SMTP_PORT` (default 587), `DQ_SMTP_USER`, `DQ_SMTP_PASSWORD`, `DQ_ALERT_TO`.

## Review Focus

1. CSV headers with spaces, quotes, or SQL-looking text (`"order id"`, `a"b`, `drop table`) → they load and check like any column (test in Task 2, Task 4).
2. A header-only CSV (zero rows) or a UTF-8 BOM → loads 0 rows without error; `row_count` fails normally (test in Task 2).
3. URL or API that hangs or returns 500 → fetch error recorded within 30 s timeout; no load (test in Task 5).
4. LLM returns prose, broken JSON, or rules naming unknown columns → those are dropped; chat shows a friendly message, not a 500 (test in Task 9).
5. Sensor ticks again while a source's run is still queued or running → no duplicate run for the same slot (test in Task 8).

### Task 2: Schema inference and staging (cast + `_raw`)

**Files:**
- Create: `dqwatch/schema.py`
- Test: `tests/test_schema.py`

**Interfaces:**
- Produces: `TYPES = {"integer": "BIGINT", "number": "DOUBLE", "text": "VARCHAR", "boolean": "BOOLEAN", "date": "DATE", "timestamp": "TIMESTAMP"}`; `qi(name: str) -> str` (double-quote, escape `"` as `""`); `infer_columns(csv_bytes: bytes) -> list[Column]`; `preview(csv_bytes: bytes, n: int = 20) -> list[dict]` (values as strings); `stage(con: duckdb.DuckDBPyConnection, csv_bytes: bytes, columns: list[Column], key: str | None) -> StageReport`.
- `stage` creates/overwrites temp table `staging` with: each configured column via `TRY_CAST` to its type; `_raw VARCHAR` = JSON of the original row **only when any non-empty value failed to cast**, else NULL; `_row_hash VARCHAR` = md5 of the original values joined; `_row_idx BIGINT` = file order. Missing configured columns → NULL. Extra file columns → listed in `new_columns`, not staged. If `key` is set: rows with empty/NULL key are removed and returned in `null_key_rows` (original values as dict). Duplicate keys keep the highest `_row_idx` and `duplicate_keys` = number of rows dropped.
- Read CSV with DuckDB `read_csv(..., all_varchar=true, header=true)` from a temp file. Unparseable or zero-column input → raise `ValueError`.

### Task 4: Rule validation and evaluation

**Files:**
- Create: `dqwatch/rules.py`
- Test: `tests/test_rules.py`

**Interfaces:**
- Produces:
  - `RULE_TYPES = {"not_null", "unique", "range", "allowed", "pattern", "row_count", "freshness"}`
  - `PATTERNS = {"email": r"^[^@\s]+@[^@\s]+\.[^@\s]+$", "date": r"^\d{4}-\d{2}-\d{2}$", "digits": r"^\d+$"}`
  - `validate_rule(rule: dict, columns: list[Column]) -> dict`: returns a normalized copy, default `severity="error"`, raises `ValueError` with a plain-English message. Params: `column` (must exist; freshness may also use `_loaded_at`, its default), `range: min?/max?` (at least one), `allowed: values: list`, `pattern: preset ∈ PATTERNS`, `row_count: min: int`, `freshness: max_age_hours: number` (column must be date/timestamp/_loaded_at).
  - `evaluate(con, table: str, rule: dict, batch_id: str | None, now: datetime) -> CheckResult`. Scope: `not_null|range|allowed|pattern|row_count` filter `_batch_id = batch_id`; `unique|freshness` use the whole table. Row rules return `failing_count` + up to 5 failing rows as `sample`. `row_count` fails when count < min. `freshness` fails when `max(column)` is older than `now - max_age_hours` or the table is empty. Pattern casts the column to VARCHAR; NULLs don't fail pattern/range/allowed (not_null covers them).
  - `schema_result(report: StageReport) -> CheckResult` (`rule_id="schema"`, severity error, fails if `cast_failed_rows`, `missing_columns`, `new_columns` or `null_key_rows`; `detail` lists which, in plain English).
  - `duplicate_keys_result(report) -> CheckResult` (`rule_id="duplicate_keys"`, severity warn).

### Task 7: Pipeline (the non-blocking guarantee)

**Files:**
- Create: `dqwatch/pipeline.py`
- Test: `tests/test_pipeline.py`

**Interfaces:**
- Consumes: Tasks 1–6.
- Produces: `run_source(meta_con, duck_con, source_id: int, inbox_root: str, now: datetime, smtp: SmtpConfig | None = None, send=None) -> str`. Returns the run status: `loaded | no_change | fetch_error`.

Flow (the order is the guarantee):
1. `start_run`. `fetch`. On `FetchError`: record `CheckResult("fetch","error","error",detail=str(e))`, then go to step 5.
2. For each `(item, bytes)` whose `fingerprint_changed`: `batch_id = uuid4().hex`; `schema.stage` (a `ValueError` → record a `fetch` error for that item, continue); `load.ensure_table` + `load.load`; `record_fingerprint`; `add_attention` for each null-key row (reason `"missing key"`); `update_sample(preview rows)`. **Load commits here.**
3. After commit, for that batch: record `schema_result`, `duplicate_keys_result` (only if `source.key_column`), and each rule via `rules.evaluate`. Each evaluate is wrapped in its own `try/except Exception` → `CheckResult(rule_id, "error", severity, detail=repr(e))`.
4. If no item changed: evaluate only `freshness` rules (whole table, if the table exists). Status `no_change`.
5. Notify: collect results with severity `error`, status `fail|error`, whose `last_status` (read before recording) was `pass` or None. If any and `smtp`: `send_alert` inside `try/except` → on failure record `CheckResult("email","error","warn",detail=...)`. Never re-raise.
6. `finish_run`. Only an exception from step 2's `load.load` itself is re-raised (after `finish_run(..., "load_failed")`), so Dagster shows a real failure.

  - `test_crashing_check_does_not_block`: monkeypatch `rules.evaluate` to raise → rows still in the table, result status `error`, run finished.
  - `test_smtp_failure_does_not_block`: `send` raises → rows loaded, an `email` result recorded, no exception.

  - `test_schema_mismatch_lands`: `amount=N/A` → row loaded with NULL amount, `schema` result `fail`.
